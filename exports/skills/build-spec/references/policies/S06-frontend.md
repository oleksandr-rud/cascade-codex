# S06 — Frontend and interaction

Adapt IDEF8's action-response viewpoint into concrete UI contracts. Define routes,
screens, components, data dependencies, forms and validation, primary actions,
navigation, loading/empty/error/success states, permissions, responsive behavior
and accessibility. Bind an accepted design or provide concrete layout/component
decisions; an interaction diagram alone is not a visual specification.

The section contains screen/component records and the interaction diagram.
Every server action references an operation ID and its response/error mapping.
Represent completion and recovery honestly; disabling a button is not backend
authorization or concurrency enforcement.

Check that each in-scope user task can complete and recover using specified
screens. See [interaction guidance](../../../spec-diagrams/references/interaction-company.md).
