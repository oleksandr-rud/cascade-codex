# Proportionate process examples

These are illustrative synthetic commissions, not receipts of target work,
participant research or accepted design. Actual artifacts are needed before
creation READY. The full local corpus can be loaded at each relevant phase.

## One accepted spacing correction

Input: accepted desktop form/frame and an explicit instruction to align its
submit row with the existing field grid. Inspect the frame and governing token,
bind the affected viewport/state, adjust the editable artifact, render and compare.
Reuse existing type, palette, components and behavior. No new market research,
brand alternatives, participant interview or system-wide token revision is needed.
Handoff the exact corrected frame and any remaining mismatch.

## A new parameter flow in an existing product

Input: actual object/parameter model, existing editor, accepted design rules and
known save/unsaved behavior. Reuse that brief; inspect what information/action
the user needs at selection, valid edit, invalid edit and switch/cancel/recovery.
Choose controls by value type/constraints, not a generic marketing layout. Map
the affected state/viewport pairs, create editable previews and inspect them.
Do not invent autosave, a cart, sharing or accounts. If switching behavior is
unknown, ask only that material product question and continue independent layout
work. A local fixture can rehearse transitions but cannot establish persistence.

## An explicitly open new experience

Input: grounded audience/job, content and constraints, plus authorization to
choose a new direction. Research only uncertainties that affect the design.
Map IA/critical paths, then compare a small number of structurally distinct
directions using representative actual artifacts. Use existing delegation or
the user's decision once, record one coherent direction, and prototype required
states/widths. Local style data guides options; no random service or independent
master file is required. Missing render access leaves an artifact gap.

## Source-only accessibility review

Input: supplied component markup/behavior without browser or assistive receipts.
Review semantics, labels and potential interaction risks; bind exact criteria
and disposition any scan. A coherent review can be READY with keyboard/focus/AT
checks PLANNED. Do not report those checks PASS or claim full compliance. A new
implementation fix belongs to the host owner.

## Approved comp reproduction

Input: accepted frame/version and an actual implementation capture. Bind matched
viewport/state/theme/content/font/asset conditions; compare regions and classify
differences. The host repairs observed mismatches and returns a fresh capture.
Source/build tests alone cannot establish fidelity. A missing required reference
or capture stays GAP/BLOCKED; widening tolerance or updating baseline cannot
self-approve the implementation.

## Explicit reference update

Input: chosen upstream pin and a concrete benefit. Acquire inert text, compare
license/behavior deltas, adapt procedures into the same controller, preserve
notices and hashes, run affected integrity/contracts/catalog checks and obtain
independent review. The integration owner stages exact accepted paths and commits
the coherent revision. Invocation never auto-downloads or installs an updater.
