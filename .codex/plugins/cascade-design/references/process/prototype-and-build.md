# Prototype and build

Create Design authors reviewable presentation artifacts. The host supplies tools,
paths, external-write authority and the production owner. A prototype's local
interaction is not an implemented backend, permission system or accepted feature.

## Bind before making

Carry the existing brief, chosen direction, governing sources, interaction map,
required viewport/state pairs and delivery format. Use actual supplied data or
clearly labeled non-sensitive fixtures. Distinguish known rules from assumptions;
do not invent commercial claims, participant quotes or operational confirmation.

Choose the fastest adequate editable format within authorization. An isolated
HTML/CSS presentation with local state or SVG plus viewable preview works when
format is open. A requested Figma/native/tool-specific deliverable requires the
actual corresponding tool and usable output. If it is unavailable, report
BLOCKED rather than substituting an imagined tool action. A read-only planning
request stays a plan with artifact gaps.

## Compose the useful path

1. Start with the actor's current task, useful result, necessary information,
   primary action and truthful completion/recovery. The first visible region
   should explain the decision without narrating implementation work.
2. Use accepted components/tokens/assets before creating replacements. Establish
   alignment, hierarchy, type rhythm, density, contrast and spacing. Add a
   container only when it communicates an independent object, boundary or action.
3. Match controls to domain decisions using [domain controls](../topics/domain-controls.md).
   Specify labels/units, input constraints, defaults, dependencies, consequences,
   validation, selected state, keyboard/focus and disabled reasons.
4. Define state transitions concretely: initial values, edit/selection, validation,
   loading/pending, empty/partial, failure, blocked permission, retry, success,
   unsaved work and return/resume where applicable. A success message represents
   only the operation actually established by this artifact or supplied evidence.
5. Make a bounded responsive rule: information priority, wrap/reflow, minimum
   content widths, table/card behavior, action placement and touch/keyboard
   access. Use actual requested pairs, not a compulsory Cartesian product of
   every possible state and viewport.
6. For structured choices, summaries or contextual results, use the local
   [Generative UI practice](../../skills/design-system/references/generative-ui.md)
   when it helps the job. Supported components, data provenance and local state
   stay explicit; no live agent/backend dependency is implied.

## Produce artifacts incrementally

Build the critical region and path first, then required dependent states. Use
local fixtures to demonstrate supported transitions, preserving the distinction
between visual rehearsal and integration. Ensure an editable source corresponds
to each required preview. Shared layout rules can guide other states but cannot
replace required frames. Keep source/preview revisions synchronized.

Use the [platform and component guidance](../topics/platforms-and-components.md)
and full local references for content, type, spacing, interaction, responsive and
platform details. Examples are subordinate to the actual target version and
primitives. Copying code does not grant installation, production writes, external
fonts/images or API execution. Do not ship a foreign demo checkout, generated
customer data, hook, runtime engine or telemetry.

Record asset origin/license, chosen font fallback, token mapping and unavailable
assets. A remotely named font/icon/image is not acquired or licensed merely
because a dataset recommends it. Existing Hybrid/generative demonstration assets
remain optional local references, not target functionality.

## Render and inspect

Render at each declared viewport/state with expected content, theme, locale,
font/asset load and relevant zoom/DPR. Inspect the actual image or runnable surface.
Check layout fit, hierarchy, text, action, overflow, state, focus and responsive
behavior. For a required interaction, exercise the actual prototype path when
available and record what is local simulation. Correct evident defects and
recapture the affected pairs.

Follow [review and evidence](review-and-evidence.md) for region comparison,
diagnosis and finite recovery. If the environment cannot render or inspect a
required preview, expose that limit; code/source review alone cannot make
creation READY or establish pixel fidelity.

## Handoff the exact candidate

Use the [handoff template](../templates/design-handoff.md) and existing structured
schema. Bind governing source IDs, frame IDs, editable/preview locators, revisions,
capture conditions, required pair coverage, interaction/responsive rules,
assets/tokens, deviations, gaps and the next owner. Reuse target-owned truth
files rather than creating a new global fact system.

Creation READY means all required pairs have inspected artifacts and a coherent
handoff. It is distinct from approved design, production implementation and
functional/user acceptance. The implementation owner consumes the accepted
version and returns exact matched evidence for downstream comparison.
